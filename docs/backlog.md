# Инженерный backlog AI Task Manager

Дата обновления: 2026-05-17

Этот backlog переводит roadmap и аудит продукта в конкретные инженерные задачи. Он предназначен для будущих агентов: у каждой задачи есть границы реализации, зависимости, основные файлы и проверяемые критерии приемки.

## Эпик 1. Ежедневный web-сценарий

Цель: сделать первый экран после входа полноценным рабочим местом для планирования дня.

### FE-001: Today Dashboard

Приоритет: P0  
Сложность: M  
Статус: готово к постановке как `TASK-004`

Границы реализации:
- Перестроить первый экран после входа вокруг дневного плана.
- Показать задачи на сегодня, просроченные задачи, ближайшие события и статус интеграций.
- Добавить состояния загрузки, ошибки и пустого списка.
- Не менять backend-контракты, если существующих `/api/tasks`, `/api/events`, `/api/integrations`, `/api/sync/state` достаточно.

Основные файлы:
- `frontend/src/App.tsx`
- `frontend/src/index.css`
- `frontend/src/App.test.tsx`

Зависимости:
- Текущие endpoints задач, событий и интеграций.

Критерии приемки:
- Пользователь после входа видит план на сегодня без перехода на другие экраны.
- Просроченные задачи визуально отделены от задач на сегодня.
- Пустые состояния объясняют отсутствие задач, событий или подключенных интеграций.
- Ошибка загрузки видна пользователю в UI.
- `npm --prefix frontend run test` проходит.

### FE-002: Видимые ошибки API в web UI

Приоритет: P0  
Сложность: S

Границы реализации:
- Добавить единый способ показывать ошибки загрузки, сохранения интеграций, создания задач и редактирования событий.
- Ошибки не должны оставаться только в `console.error`.
- Не добавлять глобальную систему уведомлений, если достаточно локальных error blocks в текущем UI.

Основные файлы:
- `frontend/src/App.tsx`
- `frontend/src/App.test.tsx`

Зависимости:
- Можно делать вместе с `FE-001`.

Критерии приемки:
- При падении `/api/tasks` или `/api/events` пользователь видит сообщение об ошибке.
- При ошибке `POST /api/tasks` введенный текст задачи не теряется.
- При ошибке сохранения интеграций пользователь понимает, что токены не сохранены.
- Тесты покрывают хотя бы одну ошибку загрузки и одну ошибку мутации.

### FE-003: Разделение `App.tsx` на компоненты

Приоритет: P1  
Сложность: M

Границы реализации:
- Выделить компоненты auth, integrations, dashboard/tasks и calendar.
- Сохранить существующее поведение.
- Не менять визуальный стиль радикально.

Основные файлы:
- `frontend/src/App.tsx`
- новые файлы в `frontend/src/components/`

Зависимости:
- Лучше выполнять после `FE-001`, чтобы не рефакторить UI дважды.

Критерии приемки:
- `App.tsx` остается координатором состояния, но не содержит весь JSX приложения.
- Существующие frontend-тесты проходят.
- Добавлены или обновлены тесты для вынесенных пользовательских сценариев.

## Эпик 2. Жизненный цикл задач

Цель: пользователь должен управлять задачами полностью из AI Task Manager, без обязательного перехода в Todoist.

### TASKS-001: Backend endpoints для обновления, завершения и удаления задач

Приоритет: P0  
Сложность: M  
Статус: часть `TASK-005`

Границы реализации:
- Добавить endpoints для update, complete и delete задачи.
- Расширить `TodoistService` методами, которые соответствуют Todoist API.
- Обновлять локальный кэш после успешной мутации.
- Возвращать понятные HTTP-ошибки вместо молчаливого `None`, где возможно.

Основные файлы:
- `backend/main.py`
- `backend/services/todoist_service.py`
- `backend/services/db_service.py`
- `backend/tests/test_api.py`
- `backend/tests/test_todoist_service.py`

Зависимости:
- Текущая модель cached tasks.

Критерии приемки:
- API позволяет изменить содержимое, срок и приоритет задачи.
- API позволяет завершить задачу и убрать ее из активного кэша.
- API позволяет удалить задачу и убрать ее из активного кэша.
- Ошибки Todoist возвращаются как контролируемые HTTP-ответы.
- Backend-тесты покрывают успешные и ошибочные сценарии.

### TASKS-002: Frontend-действия для редактирования, завершения и удаления задач

Приоритет: P0  
Сложность: M  
Статус: часть `TASK-005`

Границы реализации:
- Добавить UI-действия для edit, complete и delete.
- Обновлять список задач после успешной мутации.
- Показывать ошибку, если мутация не прошла.
- Не добавлять сложную bulk-работу с задачами в этой задаче.

Основные файлы:
- `frontend/src/App.tsx`
- `frontend/src/index.css`
- `frontend/src/App.test.tsx`

Зависимости:
- `TASKS-001`.

Критерии приемки:
- Задачу можно отредактировать из UI.
- Задачу можно завершить из UI, после чего она исчезает из активного списка.
- Задачу можно удалить из UI после явного пользовательского действия.
- Ошибки мутаций видны пользователю.
- Frontend-тесты покрывают новые действия.

### TASKS-003: Длительность задач

Приоритет: P0  
Сложность: M  
Статус: готово к постановке как `TASK-006`

Границы реализации:
- Добавить `duration_minutes` в backend response и локальный кэш.
- Поддержать старые задачи без длительности.
- Добавить выбор длительности при создании и редактировании задачи.
- Использовать варианты 15, 30, 45, 60, 90 минут.

Основные файлы:
- `backend/services/db_service.py`
- `backend/main.py`
- `frontend/src/App.tsx`
- `backend/tests/test_api.py`
- `frontend/src/App.test.tsx`

Зависимости:
- Лучше делать после или вместе с lifecycle задач, чтобы редактирование длительности имело UI.

Критерии приемки:
- `/api/tasks` возвращает `duration_minutes`.
- Создание задачи может принять `duration_minutes`.
- Старые cached tasks без длительности возвращаются без ошибки.
- UI позволяет выбрать длительность из стандартных вариантов.
- Backend- и frontend-тесты покрывают новое поле.

## Эпик 4. Auto Schedule и планирование

Цель: дать пользователю безопасное автоматическое планирование дня с подтверждением перед записью в календарь.

### PLAN-001: Расчет свободных окон календаря

Приоритет: P1  
Сложность: M  
Статус: часть `TASK-007`

Границы реализации:
- Добавить API для получения свободных окон в выбранный день.
- Учитывать события календаря, рабочие часы и timezone.
- Вернуть deterministic результат без LLM.

Основные файлы:
- `backend/main.py`
- `backend/services/gcal_service.py`
- новый модуль планировщика, если потребуется
- `backend/tests/test_scheduler.py`

Зависимости:
- Настройки рабочего дня можно временно задать дефолтами, если отдельной модели еще нет.

Критерии приемки:
- API возвращает список свободных окон для выбранной даты.
- Занятые события не пересекаются со свободными окнами.
- All-day события обрабатываются явно.
- Тесты покрывают пересечения, пустой календарь и полностью занятый день.

### PLAN-002: Предварительный план задач

Приоритет: P1  
Сложность: L  
Статус: часть `TASK-007`

Границы реализации:
- Разместить задачи в свободные окна с учетом длительности, срока и приоритета.
- Вернуть preview без создания Google Calendar событий.
- Добавить короткое объяснение для каждого размещения.
- Не использовать LLM как единственный источник расписания.

Основные файлы:
- `backend/main.py`
- `backend/services/scheduler.py`
- `backend/tests/test_scheduler.py`

Зависимости:
- `TASKS-003`.
- `PLAN-001`.

Критерии приемки:
- API возвращает proposed schedule для выбранного дня.
- Задачи без длительности получают понятный fallback или попадают в список unplanned.
- Предложения не пересекаются с существующими событиями.
- Ответ содержит причины размещения или причину, почему задача не запланирована.

## Эпик 6. Надежность, безопасность и эксплуатация
