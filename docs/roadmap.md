# Roadmap продукта AI Task Manager

Дата обновления: 2026-05-17

## Цель roadmap

Roadmap описывает путь от текущего прототипа к зрелому персональному сервису планирования дня. Основной фокус: сначала сделать надежный ежедневный сценарий для одного пользователя, затем добавить автоматическое планирование и только после этого развивать SaaS-возможности.

## Принципы приоритизации

- P0: без этого продукт не решает базовый пользовательский сценарий или несет высокий эксплуатационный риск.
- P1: усиливает ценность продукта после стабилизации базового сценария.
- P2: готовит продукт к масштабированию, коммерциализации или командному использованию.
- Research: идея требует проверки UX, технического подхода или рыночной ценности до постановки как engineering task.

Оценка сложности:
- S: 1-2 дня, локальное изменение.
- M: 3-5 дней, несколько модулей или заметные тесты.
- L: 1-2 недели, сквозной сценарий или изменение архитектуры.
- XL: больше 2 недель, требует декомпозиции перед реализацией.

## Now

Задачи этого блока должны идти первыми. Они превращают текущий web UI из набора интеграционных панелей в понятный ежедневный продукт.

| Пункт | Приоритет | Пользовательский результат | Сложность | Зависимости | Следующая инженерная задача |
| --- | --- | --- | --- | --- | --- |
| Today Dashboard | P0 | После входа пользователь сразу видит задачи на сегодня, просроченные задачи, ближайшие события и состояние интеграций. | M | Текущие `/api/tasks`, `/api/events`, `/api/integrations`, `/api/sync/state` | `TASK-004` |
| Полный жизненный цикл задач | P0 | Пользователь может создать, изменить, завершить и удалить задачу без перехода в Todoist. | L | Todoist API methods, локальный кэш задач, видимые ошибки UI | `TASK-005` |
| Длительность задач | P0 | Пользователь указывает, сколько времени занимает задача, а продукт может использовать это в планировании. | M | Расширение модели задачи, совместимость старых задач, UI формы задачи | `TASK-006` |
| Видимые ошибки и пустые состояния | P0 | Пользователь понимает, почему нет задач/событий и что нужно сделать для восстановления синхронизации. | M | Today Dashboard, sync state, интеграции | Включить в `TASK-004` или выделить отдельную задачу после него |
| Стабилизация синхронизации после мутаций | P0 | После создания, изменения или завершения задачи UI показывает актуальное состояние без ручного обхода ошибок. | M | Полный жизненный цикл задач, `sync_state`, обработка ошибок Todoist | Включить в `TASK-005` |

### Definition of Done для Now

- Главный экран отвечает на вопрос "что делать сегодня".
- Все изменения задач доступны из web UI.
- У задач есть длительность или корректный fallback.
- Ошибки интеграций показываются пользователю, а не только пишутся в логи.
- Frontend и backend тесты покрывают новые пользовательские сценарии.

## Next

Задачи этого блока стоит начинать после P0-стабилизации. Они добавляют ключевую дифференциацию продукта: автоматическое планирование и нормальное подключение интеграций.

| Пункт | Приоритет | Пользовательский результат | Сложность | Зависимости | Следующая инженерная задача |
| --- | --- | --- | --- | --- | --- |
| Auto Schedule v1 | P1 | Пользователь получает предложенный план дня по свободным окнам календаря и подтверждает его до записи событий. | L | Длительность задач, календарные события, настройки рабочего дня, deterministic scheduler | `TASK-007` |
| Google OAuth Flow | P1 | Пользователь подключает Google Calendar из UI без ручной вставки `token.json`. | L | Модель интеграций, безопасное хранение токенов, callback endpoint | Backlog: `Google OAuth Flow` |
| Dashboard состояния синхронизации | P1 | Пользователь видит время последней синхронизации, последнюю ошибку и может переподключить интеграцию. | M | Расширенный `sync_state`, видимые ошибки, Today Dashboard | Backlog: `Dashboard состояния синхронизации` |
| AI-парсинг задач в web UI | P1 | Пользователь вводит задачу обычным языком, а продукт предлагает название, срок, длительность и приоритет. | M | Длительность задач, существующий `AIService`, UI подтверждения результата | Backlog: `AI-парсинг задач` |
| Настройки планирования | P1 | Пользователь задает рабочие часы, timezone и календарь для планирования. | M | Auto Schedule v1, модель пользовательских настроек | Новая задача после `TASK-007` |
| Production hardening базы | P1 | Команда может безопасно менять схему данных и проверять ее в тестах. | L | Alembic или аналог миграций, PostgreSQL integration tests | Новая инфраструктурная задача |

### Definition of Done для Next

- Auto Schedule не записывает события без подтверждения.
- Google Calendar подключается через понятный OAuth flow.
- Состояние интеграций диагностируемо из UI.
- AI помогает создавать задачи, но пользователь подтверждает результат.
- Изменения схемы БД проходят через миграции.

## Research

Эти идеи нельзя ставить в реализацию без короткой проверки гипотезы или технического spike.

| Идея | Почему это research | Проверка перед реализацией |
| --- | --- | --- |
| Автоматический перенос незавершенных задач | Нужны правила UX: переносить автоматически, спрашивать пользователя или предлагать варианты. | Прототип вечернего review flow. |
| LLM-оптимизация расписания | Есть риск недетерминированных и неверных планов. Базовое размещение должно быть deterministic. | Сравнить deterministic scheduler и LLM explanations на наборе fixtures. |
| Командные сценарии | Текущий продукт еще не доказал персональный сценарий. | Описать 2-3 реальные team use cases и требования к ролям. |
| Платные тарифы | Пока не ясно, какие функции создают устойчивую premium-ценность. | Сопоставить тарифы с validated value: auto-schedule, analytics, team planning. |

## Рекомендуемый порядок реализации

1. `TASK-004: Today Dashboard`
2. `TASK-005: Полный жизненный цикл задач`
3. `TASK-006: Длительность задач`
4. `TASK-007: Auto Schedule v1`
5. `Google OAuth Flow`
6. `Dashboard состояния синхронизации`
7. `AI-парсинг задач`
8. `Production hardening базы`

## Зависимости между ключевыми блоками

- `TASK-007: Auto Schedule v1` зависит от `TASK-006`, потому что планировщику нужна длительность задач.
- `Dashboard состояния синхронизации` лучше делать после `TASK-004`, чтобы не создавать отдельный экран без главного пользовательского контекста.
- `Google OAuth Flow` можно делать параллельно с `TASK-005` или после него, но до публичного использования Google Calendar.
- `AI-парсинг задач` лучше делать после появления длительности и редактирования задач, иначе пользователю негде исправить результат парсинга.
- Workspace, billing и analytics не должны начинаться до стабилизации персонального сценария.

## Ближайшие критерии зрелости продукта

- Пользователь может подключить Todoist и Google Calendar без ручных технических артефактов.
- Пользователь может управлять задачами и видеть план дня полностью из web UI.
- Продукт не молча скрывает ошибки интеграций.
- Автоматическое планирование предлагает, но не применяет изменения без подтверждения.
- Схема данных управляется миграциями и проверяется интеграционными тестами.
