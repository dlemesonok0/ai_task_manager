# Быстрая локальная разработка

Для ускорения цикла обратной связи при разработке можно запускать backend и frontend напрямую, без пересборки Docker-образов при каждом изменении кода.

## Общие требования

- **PostgreSQL** — единственная внешняя зависимость, которую удобно держать в Docker (контейнер собирается один раз, затем стартует быстро).
  ```bash
  docker compose up -d postgres
  ```
  После этого БД будет доступна на `localhost:15432` (порт из `docker-compose.yml`).

- **Переменные окружения** — скопируйте `.env.example` в `.env` и при необходимости отредактируйте под локальный запуск (например, оставить `DATABASE_URL` как есть, если запустили postgres через compose).

## Backend (Python/FastAPI)

### Запуск с автоперезагрузкой

```bash
uv run uvicorn main:app --reload
```

- Сервис будет доступен на `http://localhost:8000`.
- При изменении любого Python-файла сервер перезагружается мгновенно.
- Требуется только установленная рабочая директория с активированным виртуальным окружением через `uv sync` (выполнить один раз после клонирования репозитория).

### Тесты

Все backend-тесты используют `FakeDatabase` через `monkeypatch` и не требуют реальной PostgreSQL или внешних сервисов.

```bash
uv run pytest
```

Если захотите запустить тесты против реальной БД (для отладки схемы или сложных запросов), сначала убедитесь, что PostgreSQL запущен, затем:

```bash
uv run pytest -m postgres
```

(Предполагается, что такие тесты будут помечены маркером `postgres`; пока таких тестов нет, но можно добавить в дальнейшем.)

### Полезные команды

- `uv sync` — (один раз) установить зависимости.
- `uv run uvicorn main:app --reload` — запустить API с хот-релоадом.
- `uv run pytest` — запустить все unit-тесты.
- `uv run pytest --cov` — запустить тесты с покрытием.
- `uv run mypy .` — проверить типы (если настроено).
- `uv run ruff check` — линтер.

## Frontend (React/Vite)

### Запуск dev-сервера

```bash
npm run dev
```

- Приложение будет доступно на `http://localhost:5173`.
- Hot Module Replacement (HMR) обеспечит мгновенное обновление UI при изменении React-компонентов, стилей и т.п.
- Требуется только один раз выполнить `npm install`.

### Тесты

```bash
npm test
```

Запускает Vitest в режиме запуска (не watch). Тесты используют `jsdom` и мокируют `fetch` глобально, не требуя реального бэкенда.

### Полезные команды

- `npm install` — (один раз) установить зависимости.
- `npm run dev` — запустить dev-сервер с HMR.
- `npm test` — запустить тесты один раз.
- `npm run test:watch` — запустить тесты в режиме наблюдения (если добавлен в package.json).
- `npm run lint` — проверить код ESLint.
- `npm run build` — собрать продакшен-версию (Vite + TypeScript).
- `npm run preview` — предпросмотр собранной сборки локально.

## Рабочий процесс

1. **Одновременно запустите** (в разных терминалах или через табы/tmux):
   - Backend: `uv run uvicorn main:app --reload`
   - Frontend: `npm run dev`
   - PostgreSQL (если ещё не запущен): `docker compose up -d postgres`

2. **Откройте** приложение в браузере по адресу `http://localhost:5173`. Оно будет автоматически подключаться к локальному бэкенду на `http://localhost:8000` (поскольку `VITE_API_URL` по умолчанию пустой, а бэкенд на том же хосте, но другом порту).

3. **Изменяйте код**:
   - Изменения в backend Python-файлах приведут к мгновенной перезагрузке uvicorn-сервера.
   - Изменения в frontend TSX/CSS/TS файлах приведут к HMR-обновлению в браузере без полной перезагрузки страницы.
   - Логи обоих процессов будут выводиться в соответствующих терминалах.

4. **Запускайте тесты** по мере необходимости:
   - В отдельном терминале: `uv run pytest` (backend) и `npm test` (frontend).
   - Оба набора тестов работают быстро (секунды) благодаря использованию фейков зависимостей и отсутствию необходимости в реальных внешних сервисах.

## Советы по ещё более ускоренной работе

- **Избегайте лишних перезапусков контейнеров**: запускайте только PostgreSQL через Docker, а бэкенд и фронтенд — напрямую на хосте.
- **Используйте `uv sync` только при изменении зависимостей**: после `git pull` проверяйте, не изменились ли `pyproject.toml` или `package.json`, и только тогда выполняйте синхронизацию пакетов.
- **Локальные переменные окружения**: если вам нужно часто переключаться между разными конфигурациями (например, отключать某些 интеграции для отладки), храните несколько `.env.*` файлов и копируйте нужный в `.env` перед запуском.
- **Отладка через логи**: поскольку сервисы запускаются в терминале, все `print` и `logger` сообщения будут видны сразу, без необходимости заходить в логи контейнера.

## Что НЕ нужно делать для быстрой локальной разработки

- **Не пересобирайте Docker-образы** при каждом изменении кода (`docker compose build` или аналогичные команды).
- **Не запускайте весь стек через `docker compose up`** во время активной разработки, если только вы не проверяете взаимодействие всех сервисов в production-подобной среде (это медленнее из-за пересборки и multi-stage builds).
- **Не используйте `docker compose restart`** для применения изменений кода — перезапуск контейнера не увидит новый код, пока образ не будет rebuilt.

Этот подход обеспечивает цикл обратной связи в пределах секунд для большинства правок кода, что значительно ускоряет итерацию по сравнению с полным redeploy через контейнеры.
