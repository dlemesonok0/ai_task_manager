# Аудит продукта AI Task Manager

Дата аудита: 2026-05-17

## Краткое резюме

AI Task Manager уже имеет рабочий каркас персонального планировщика: веб-интерфейс, FastAPI backend, PostgreSQL-кэш, авторизацию, интеграции с Todoist и Google Calendar, Telegram-бота, JSON-логи и Docker Compose для запуска сервиса.

Текущий продукт больше похож на технический прототип, чем на зрелый сервис. Основная ценность видна: пользователь может подключить интеграции, увидеть задачи и календарь, создать задачу и отредактировать событие. Но не хватает полного жизненного цикла задач, понятного дневного сценария, надежного подключения Google OAuth, управляемой синхронизации, безопасной работы с секретами и production-ready миграций/наблюдаемости.

## Текущие возможности

### Backend API

- FastAPI-приложение с health endpoint `/`.
- Регистрация, вход и проверка текущего пользователя:
  - `POST /api/auth/register`
  - `POST /api/auth/login`
  - `GET /api/auth/me`
- Bearer-токены на HMAC-подписи с TTL из `AUTH_TOKEN_TTL_SECONDS`.
- CRUD-часть интеграций:
  - `GET /api/integrations`
  - `PUT /api/integrations`
- Синхронизация локального кэша:
  - `POST /api/sync`
  - `GET /api/sync/state`
- Чтение и создание задач:
  - `GET /api/tasks`
  - `POST /api/tasks`
- Чтение и редактирование календарных событий:
  - `GET /api/events`
  - `PATCH /api/events/{event_id}`
- Чтение и скачивание логов:
  - `GET /api/logs`
  - `GET /api/logs/download`

### Хранилище данных

- PostgreSQL используется как основное локальное хранилище.
- Таблицы создаются кодом при старте приложения:
  - `users`
  - `user_integrations`
  - `cached_tasks`
  - `cached_events`
  - `sync_state`
- Кэш задач и событий привязан к `user_id`.
- Секреты интеграций хранятся в `user_integrations`.
- Есть простое состояние синхронизации по ресурсам `tasks` и `events`.

### Frontend

- React/Vite SPA.
- Экран входа и регистрации.
- Хранение access token в `localStorage`.
- Настройка Todoist API token, Google token JSON и Telegram bot token.
- Индикаторы подключенности интеграций.
- Ручная синхронизация через кнопку `Refresh`.
- Создание новой Todoist-задачи из формы.
- Группировка задач по срокам:
  - Today
  - Tomorrow
  - Upcoming
  - No due date
- Недельный календарный вид с таймлайном с 07:00 до 22:00.
- Редактирование названия и времени Google Calendar события через модальное окно.

### Интеграции

- Todoist:
  - получение активных задач;
  - создание задач;
  - создание inbox-задач;
  - закрытие задачи реализовано в сервисе, но не выведено в API/UI.
- Google Calendar:
  - получение ближайших событий из всех доступных календарей;
  - создание событий;
  - обновление событий;
  - поддержка token JSON из пользовательских интеграций;
  - fallback на локальный `token.json` и `credentials.json`.
- AI:
  - парсинг текстовой задачи в `content`, `due_string`, `priority`;
  - поддержка Gemini через OpenAI-compatible API, OpenAI и локального OpenAI-compatible endpoint.
- Telegram:
  - `/start`, `/help`, `/inbox`, `/briefing`, `/autoschedule`;
  - создание задач из свободного текста через AI-парсинг;
  - автопланирование через `SchedulerService`.

### Docker и эксплуатация

- `docker-compose.yml` поднимает:
  - PostgreSQL;
  - API;
  - Telegram bot;
  - frontend через nginx;
  - Dozzle для просмотра логов контейнеров.
- `docker-compose.override.yml` включает локальную сборку backend и frontend.
- Backend пишет JSON-логи в ротируемый файл и stdout.
- Frontend nginx проксирует `/api` в контейнер `api:8000`.

### Тесты

- Backend покрыт pytest-тестами для:
  - auth;
  - API задач и событий;
  - Todoist service;
  - Google Calendar service;
  - AI service;
  - Scheduler service;
  - Telegram bot.
- Backend API-тесты используют fake database через monkeypatch.
- Frontend покрыт Vitest/Testing Library для:
  - входа и регистрации;
  - сохранения интеграций;
  - загрузки задач и событий;
  - создания задачи;
  - редактирования события;
  - базовых ошибок fetch.

## Текущие пользовательские сценарии

### Регистрация и вход

1. Пользователь открывает веб-интерфейс.
2. Регистрирует аккаунт или входит по логину и паролю.
3. Frontend сохраняет bearer token в `localStorage`.
4. Все дальнейшие API-запросы отправляются с `Authorization: Bearer ...`.

Ограничения:
- нет восстановления пароля;
- нет смены пароля;
- нет logout на сервере или отзыва токенов;
- ~~дефолтные `admin/admin` могут автоматически создать пользователя, если переменные окружения не переопределены.~~ (Удалено)

### Подключение интеграций

1. Пользователь вставляет Todoist token, Google token JSON и Telegram bot token.
2. Backend сохраняет значения в PostgreSQL.
3. UI показывает булев статус подключения.
4. После сохранения frontend запускает синхронизацию.

Ограничения:
- Google OAuth не проходит через UI;
- пользователь должен вручную получить и вставить Google token JSON;
- Telegram token сохраняется, но веб-продукт не управляет запуском или привязкой бота к пользователю.

### Просмотр задач и календаря

1. После входа frontend запрашивает `/api/tasks` и `/api/events`.
2. Backend сначала читает локальный кэш.
3. Если кэш пуст или указан `refresh=true`, backend синхронизируется с внешним сервисом.
4. Если кэш уже есть, backend возвращает его и запускает фоновое обновление.

Ограничения:
- UI не показывает время последней синхронизации;
- ошибки синхронизации в UI почти не видны;
- фоновые ошибки уходят в логи, но не помогают пользователю понять состояние интеграции.

### Создание задачи

1. Пользователь вводит текст задачи в web UI.
2. Frontend отправляет `POST /api/tasks` с `due_string: today` и `priority: 1`.
3. Backend создает задачу в Todoist и добавляет ее в локальный кэш.

Ограничения:
- из web UI нельзя выбрать срок, приоритет, проект, метки или длительность;
- нельзя редактировать, завершать или удалять задачи из web UI;
- AI-парсинг задач есть в Telegram, но не подключен к web UI.

### Редактирование календарного события

1. Пользователь нажимает на событие в недельном календаре.
2. Открывается модальное окно с названием, временем начала и окончания.
3. Frontend отправляет `PATCH /api/events/{event_id}`.
4. Backend обновляет событие в Google Calendar и локальный кэш.

Ограничения:
- нельзя создать или удалить событие из UI;
- нет обработки конфликтов, повторяющихся событий, all-day событий и прав доступа;
- timezone жестко приводится через браузер и UTC в backend-сервисе.

### Telegram-сценарии

1. Пользователь пишет задачу боту.
2. AIService парсит текст.
3. TodoistService создает задачу.
4. `/briefing` показывает первые 10 активных задач.
5. `/autoschedule` генерирует расписание через LLM и сразу создает события в Google Calendar.

Ограничения:
- Telegram использует singleton-сервисы и env-токены, а не пользовательские токены из PostgreSQL;
- нет привязки Telegram-пользователя к web-аккаунту;
- `/autoschedule` применяет расписание без подтверждения пользователем.

## Недостающие части продукта

### P0: Базовая зрелость пользовательского продукта

- Today Dashboard: первый экран должен показывать план на день, просроченные задачи, ближайшие события и статус интеграций.
- Полный жизненный цикл задач: редактирование, завершение, удаление и обновление локального кэша после каждой мутации.
- Длительность задач: нужна для планирования дня и auto-schedule.

- Управление интеграциями: переподключение, удаление токена, проверка валидности токена, время последней успешной синхронизации.

### P1: Планирование и AI

- AI-парсинг задач в web UI.
- Декомпозиция крупных задач.
- Утренний и вечерний ритуал планирования.
- Dashboard синхронизации и качества интеграций.

### P2: SaaS-зрелость

- Workspace-модель.

## Продуктовые пробелы

- Нет ясного главного сценария дня. UI показывает задачи и календарь рядом, но не отвечает на вопрос "что мне делать сейчас и как выглядит мой день".
- Нет полного управления задачами. Пользователь может создать задачу, но не может закончить цикл без Todoist.
- Нет управления приоритетом, сроком и длительностью задачи из web UI.
- Нет видимого состояния синхронизации: пользователь не знает, актуальны ли задачи и события.
- Интеграции подключаются слишком технически: вставка token JSON неприемлема для обычного пользователя.
- Telegram и web выглядят как два разных продукта: Telegram работает через env singleton, web через per-user integrations.
- Auto-schedule пока не является безопасным продуктовым сценарием: бот может сразу записать события без подтверждения.
- Нет onboarding и диагностики: если токен неверный или календарь недоступен, пользователь видит пустые списки вместо понятной причины.
- Нет настроек рабочего времени, timezone, календарей, предпочтений планирования и длительности задач.
- Нет командных сценариев, хотя архитектура уже движется к multi-user.

## Технические риски

### Авторизация и безопасность

- `AUTH_SECRET_KEY` имеет небезопасное значение по умолчанию `dev-only-auth-secret`.
- ~~Fallback dmin/admin остается рабочим, если окружение не настроено.~~ (Удалено)
- Токены в `localStorage` уязвимы к XSS.
- Нет server-side сессий, refresh-токенов, отзыва токенов и смены пароля.
- Секреты интеграций хранятся в PostgreSQL как plain text.
- CORS разрешен для всех origins.
- `/api/logs` может раскрыть чувствительные данные, если они попадут в логи.

### Данные и миграции

- Схема БД создается через `CREATE TABLE IF NOT EXISTS` в runtime-коде.
- Нет версионированных миграций, rollback и контроля изменений схемы.
- Нет индексов под большинство пользовательских запросов, кроме событий по start.
- Кэш задач хранит payload JSONB, но структура доменной модели минимальна.
- Нет soft delete, audit trail и истории синхронизации.
- `upsert_task` не обновляет `sync_state`, поэтому после создания задачи состояние синхронизации может быть неполным.

### Интеграции

- Todoist errors часто превращаются в пустой список или `None`, что скрывает причину проблемы.
- Google Calendar service может запускать локальный OAuth flow из backend-процесса, что непригодно для production-контейнера.
- Google token refresh не сохраняет обновленный per-user token JSON обратно в БД.
- Telegram token в web UI сохраняется, но bot container читает `TELEGRAM_BOT_TOKEN` из env.
- Нет rate limit, retry policy, backoff и явного различения transient/permanent ошибок.

### Архитектура и эксплуатация

- Backend использует синхронный psycopg в async FastAPI endpoints; это может блокировать event loop.
- Глобальный `threading.Lock` вокруг операций БД ограничивает параллелизм.
- Сервисы частично singleton, частично per-token factory; это усложняет multi-user поведение.
- Docker Compose использует `latest` для Dozzle и `master` image tags для приложения, что снижает воспроизводимость.
- Нет healthcheck для API/frontend/bot.
- Нет CI/CD-информации в аудируемом наборе файлов, кроме локальных тестовых команд.

### Frontend

- Ошибки API в основном пишутся в `console.error`, но не показываются пользователю.
- Состояния loading/empty есть, но не покрывают частичные ошибки интеграций.
- Большая часть логики сосредоточена в одном `App.tsx`.
- Inline styles усложняют поддержку и визуальную консистентность.
- Нет маршрутизации, настроек профиля, отдельного экрана интеграций или панели диагностики.

### Тесты

- Backend API-тесты используют fake database, поэтому не ловят реальные ошибки SQL, схемы и транзакций.
- Нет тестов миграций, потому что миграций нет.
- Нет e2e-тестов через Docker Compose.
- Нет контрактных тестов внешних API или записанных fixtures для Todoist/Google.
- Frontend-тесты проверяют happy path, но мало покрывают ошибки backend и частичные сбои синхронизации.
